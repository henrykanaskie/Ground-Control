How to read the evidence in this document

Stated means the author wrote the reason down; it is quoted and cited to path:line or to a contract section. Inferred means the code constrains the reason but nobody wrote it; the observation is given first so you can disagree with the inference. Unknown means there is no evidence either way, which is reported rather than filled in. Roughly a third of the tuning constants in this repository fall in the third category, and that is one of the more useful things here.

The shape of the system

One paragraph before anything else makes sense

Ground Control is a single-process Node HTTP server with a vanilla-JS browser client and an optional native macOS shell around both. It has no persistent store: on every request it walks a directory of projects, shells out to git, reads ps and lsof, and assembles the answer in memory behind a short-lived cache. The filesystem is the database, and everything the dashboard knows is re-derived rather than recorded. Four features are bolted onto that spine — the grid and document reader, Forge (artifact generation), Workbench (editors and agent detection), and Reclaim (moving dead folders to the Trash) — each specified in its own contract document and each, by construction, appended to the same server.js and public/js/app.js rather than woven into them.

What the measured composition actually counts

  • JavaScript 80% · 1.4 MB
  • CSS 10% · 183 KB
  • Markdown 4.6% · 82.5 KB
  • Swift 2.9% · 52.5 KB
  • HTML 1.3% · 23.4 KB
  • Shell 0.5% · 8.4 KB

The remaining 0.6% is spread across file types too small to list individually.

Read that bar with one correction. Roughly two thirds of those bytes are a duplicate of the other third. GroundControl.app/ holds 25 files and 1.9 MB of the 2.9 MB total, and it is a built copy of server.js, lib/, public/ and package.json that build-app.sh places inside the bundle. It is listed in .gitignore as a build artifact, yet the scanner counted it — because lib/util.js:30's isIgnoredDir skips node_modules, *venv, and dot-directories, and knows nothing about .app bundles. The interesting part is not the inflated number; it is that Ground Control measured itself with its own ignore list and the list had a hole in it. The real source tree is closer to 39 files and 1 MB.

How much reasoning this repository actually records

Calibration — what can honestly be said and what cannot

This is an unusually well-documented codebase by the standard that matters here: six ADR-shaped contract documents totalling ~72 KB, and 90 harvested comment blocks that explain a choice rather than restate the code. Several of them cite measurements taken on the author's own machine. That supports a long document.

Two things it does not have, both of which bound what follows:

  • No git history. The directory is not a repository, so there are zero commit messages and zero commit bodies. Every "why did this change" question has to be answered from a comment that survived, or not at all. Where a comment says a value "was 3 minutes" or "was 10 minutes", that is the only record of the previous value.
  • 98 of 140 named constants carry no explanatory comment. The harvest opened 56 of 56 candidate source files, so this is silence rather than an unscanned gap — the distinction the brief format deliberately preserves.

A note on provenance

This document was produced by the code path it describes. The instruction that generated it is the string returned by designPrompt() in lib/house-style.js:374, and the factual brief it worked from is the output of buildBrief({kind:"design"}) in lib/brief.js. That brief arrived already shed to the sixth of eight budget levels — lib/brief.js:1457 — with four design documents, forty comments and a trimmed constants table, which is why the citations below were checked against the files directly rather than taken from the brief alone.

The central bet: the standard library and nothing else

Stated — CONTRACT.md, "Hard rules for every agent"

Every system rests on one commitment the rest follows from. Here it is the first line of the first contract, and it is phrased as a prohibition rather than a preference:

CONTRACT.md — hard rules

"Node.js stdlib ONLY. No npm installs, no package.json dependencies, no CDN links, no external fonts. The whole thing must run offline with node server.js. Vanilla JS on the frontend. No frameworks, no build step."

The manifest confirms it: package.json has no dependencies and no devDependencies key at all, and npm run check is four invocations of node --check rather than a linter. What makes this a bet rather than an aesthetic is that it is expensive in four specific places, and the repository paid in all four.

  • A markdown renderer written from scratch — public/js/markdown.js, supporting GFM tables, nested lists, task lists, fenced code with highlighting, footnotes and reference links. The header states the security posture that justifies the cost as well as the constraint: "every document handed to this module comes off the user's disk and is treated as hostile. Raw HTML in the source is NEVER passed through" (public/js/markdown.js:10). A dependency would have brought a configurable sanitiser; this brings a renderer that cannot be misconfigured because it has no pass-through mode.
  • No test framework — node --test test/*.test.js, 39 tests, no install step.
  • Git by subprocess, not by library — lib/git.js runs execFile with an argv array, a 5 s timeout, and an environment carrying GIT_TERMINAL_PROMPT=0, GIT_ASKPASS=echo and GIT_OPTIONAL_LOCKS=0 (lib/git.js:18–24). The last of those is the one worth stealing: reading someone else's repository must not take its index lock.
  • A 169 KB single-file frontend — public/js/app.js carries routing, the grid, the detail view, the reader and all four features' UI as one ES module, because there is no bundler to split it.

The one time the rule was lifted, and what was still refused

The macOS app is the only place the zero-dependency rule was relaxed, and the contract records both the permission and the reasoning behind refusing to use it fully:

CONTRACT-APP.md §0

"The zero-dependency rule has been lifted by the user — but do not add Electron, Tauri, or an npm toolchain anyway. […] A native shell is ~2 MB against Electron's ~150 MB, and this machine has only ~7 GB of free disk, which settles it."

That is a decision made on a machine-specific constraint and labelled as such. It is worth being precise about how weak the general form of this argument is: 150 MB against 7 GB is 2% of the disk. The reasoning is defensible for this laptop and this one app; a reader who copies "native shell beats Electron because of disk" without the 7 GB has copied the conclusion and left the premise behind. What does generalise is that the shell is genuinely thin — app/GroundControl.swift is 52.5 KB and hosts an unmodified web app, so the cost of being wrong is one file.

Decision
Node standard library only, server and client; a hand-written Swift/AppKit shell where a native app is wanted.
Forces
Must run offline with one command; must survive a moved or deleted checkout; a constrained disk; the author's stated preference for no build step.
Alternative
Express + a markdown library + a test framework + a bundler. Perhaps 300 fewer lines of framework-shaped code in lib/, at the cost of a lockfile, an install step, and a supply chain reaching a tool that reads every file in every project on the disk.
Consequence
Cheap: distribution, auditability, and offline operation. Expensive: the markdown renderer is now a permanent maintenance surface; there is no framework to absorb a routing or state change; and the frontend cannot be split without inventing a build step, which the contract forbids.

The second bet: the contract is the coordination mechanism

Stated — file-ownership tables in all six contracts

Every contract in this repository opens with the same structure: a file ownership table assigning each file to a named agent, and an instruction not to touch anyone else's. CONTRACT.md §1 assigns Agent A the backend, B the frontend, C the markdown module. CONTRACT-FORGE.md §1 adds D, E and F, and states the rule that shaped the resulting code more than any other line in the repository:

CONTRACT-FORGE.md §1

"Agents D and E both touch server.js / app.js only in their own areas — append new code, never restructure existing code."

This was written for parallel authors working from a spec without seeing each other's diffs. Nothing states that the "agents" were language models, but the shape of the constraint — no merge conflicts, no shared refactors, a written interface instead of a conversation — only makes sense when the authors cannot negotiate. Inferred

The consequences are visible in the file structure, and they are exactly what the rule asks for:

  • server.js is 56.9 KB with three banner-delimited feature sections stacked below the original server, each announcing its own compliance: "Appended below the original server. Nothing above this line was restructured; route() gained one dispatch line for /api/forge/" (server.js:486–496).
  • Comments cite contract sections the way code usually cites tickets — // (Workbench §4), // contract §4, // contract §2.5. The spec is treated as the authority, not the code.
  • Cross-feature integration happens through deliberately narrow seams. lib/jobs.js "knows nothing about subprocesses or HTML" and receives a canceller callback from lib/generate.js instead of a pid, "which keeps the dependency one-directional" (lib/jobs.js:4–7).

And the cost is equally visible. Append-only growth means the modules that gained the most features are the two largest files, and it means a stale comment is safer to leave than to fix — you can see that outcome in the drift section below. It also means public/js/app.js is a single 169 KB module carrying four features' UI, which no future contributor can split without violating either the no-build-step rule or the no-restructuring rule.

Decision
Specify each feature completely in its own contract document, assign every file a single owner, and forbid restructuring anyone else's code.
Forces
Multiple authors working in parallel with no shared working tree, no git history to merge, and no way to ask each other a question mid-build.
Alternative
One author, sequential features, refactoring freely. Smaller files and no stale rules — at the cost of the parallelism the contracts exist to buy.
Consequence
Features landed independently and the seams between them are unusually explicit. In exchange, two files are now monoliths, and correcting a rule that has changed requires editing prose in three places (the contract, the module docblock, the README) that nothing keeps in sync.

The trust boundary, and its three deliberate exceptions

Stated — CONTRACT-FORGE.md §2, CONTRACT-WORKBENCH.md §3a, CONTRACT-RECLAIM.md §0

Any tool that points itself at a folder full of other people's work has to decide what it is allowed to change. Ground Control's answer is that the default is nothing, and each departure is named, guarded and written down. There are exactly three, and they were added in increasing order of danger.

1. Writing a generated document into a project

Generation writes only to <ground-control>/.forge/<projectId>/<jobId>.html. Saving into the project is a separate POST that re-runs the path gates, accepts .html only, and returns 409 with the existing file's size and mtime rather than overwriting (server.js:939–947). The model never writes the file; Ground Control does.

2. Moving a folder to the Trash

Reclaim's governing rule is stated twice, in the contract and at the top of the module: nothing is ever permanently deleted, the destination is ~/.Trash, and the move is fs.rename. The contract also records a rejected mechanism and the experiment that rejected it:

CONTRACT-RECLAIM.md §0

"Do not use osascript/Finder automation — it triggers a macOS TCC prompt that hangs a headless server indefinitely (this was tested; it deadlocked until killed)."

Two smaller decisions inside the trash path are worth lifting out. The manifest is written to .forge/reclaim-log.jsonl before anything moves, and a failure to write it aborts the move — "No durable record ⇒ nothing moves. The log is the point" (lib/reclaim.js:1014). And the EXDEV fallback copies, fingerprints both trees, compares file/byte/dir/link counts, and only then removes the original (lib/reclaim.js:868–915). The single fs.rm in the file is reachable only after a verified copy.

3. Sending SIGTERM to a coding agent

This one replaced an absolute rule, and the contract says so in the open rather than quietly editing the old text:

CONTRACT-WORKBENCH.md §3a

"The single exception is POST /api/agents/stop. It was added deliberately, replacing an earlier absolute 'Ground Control never signals a process' rule. […] The absolute rule is replaced by four guards, all of which are required."

The guards are implemented in the order the contract lists them, in server.js:1192–1231: the pid must already be attributed to that project by a fresh sweep; the session Ground Control itself is running from is refused by ancestry (isSelf); the pid is re-verified against a live ps/lsof immediately before the signal, bypassing every cache; and only SIGTERM is ever sent. The structural move underneath is the one to take away: the process.kill call does not live in lib/agents.js. The module's header states why — "the process.kill lives in the HTTP handler, so this module's observe-only property stays intact and testable" (lib/agents.js:9–13). A property you can assert by grepping one file is worth more than the same property spread across two.

The gate all three share

Every path that crosses from a URL to the filesystem goes through one function, and it is deliberately redundant:

 * Three independent gates:
 *   1. syntactic — no absolute paths, no NUL, no `..` segment
 *   2. lexical   — path.resolve() result must be under the root
 *   3. physical  — fs.realpath() of the target (and of the root) must still be
 *                  under the real root, which defeats symlink escapes

lib/util.js:246–254. Gate 3 is the one that earns its place: gates 1 and 2 are string manipulation, and a symlink defeats string manipulation. When the target does not exist yet — the save path — the function realpaths the parent instead (lib/util.js:280–283).

The boundary that is not there

Unknown server.listen(ARGS.port) at server.js:446 passes no host, so Node binds all interfaces. There is no authentication, no token, and no Origin or Referer check anywhere in server.js; readJsonBody (server.js:519) parses the body without inspecting Content-Type. The POST surface includes launching a local editor and moving a folder to the Trash. No contract, comment or README line states a decision about the bind address or about cross-origin requests — the closest the repository comes is app/GroundControl.swift:201, which probes for a free port "on 0.0.0.0 because that is what server.listen(port) does", noting the behaviour without commenting on it. The threat model is presumably "single-user machine, trusted network", but that is my reconstruction, not the author's statement, and it is the one place in this codebase where a load-bearing security assumption is unwritten.

Talking to a model as a subprocess

Stated — CONTRACT-FORGE.md §0, §0b, §4; lib/generate.js

Forge needs a frontier model and the machine has no API key. The chosen mechanism is to shell out to the already-authenticated claude CLI in headless mode. That single choice generates most of the interesting engineering in lib/generate.js, and it is a good worked example of a general problem: when you borrow someone else's authenticated process, you inherit their configuration surface too.

Decision
Spawn the local claude CLI with child_process.spawn and an argv array; parse its stream-json events; take the artifact off stdout.
Forces
No ANTHROPIC_API_KEY on the machine; the zero-dependency rule forbids an SDK; the artifact must be verifiable against real code, which requires the model to have file tools.
Alternative
An HTTP client against the API. It would need a key (which the user does not have and the contract forbids introducing), and it would have no repository tool access, so the artifact could only be as good as the brief.
Consequence
Generation works with zero configuration and zero dependencies, and is grounded in files the model actually read. In exchange, Forge is coupled to one CLI's argv and event schema, and a version bump elsewhere on the machine can break it silently.

The environment is stripped, not just left alone

The most transferable detail here is a deletion. childEnv() copies process.env and removes six variables:

function childEnv() {
  const env = Object.assign({}, process.env);
  delete env.ANTHROPIC_API_KEY;
  delete env.ANTHROPIC_AUTH_TOKEN;
  delete env.ANTHROPIC_BASE_URL;
  // Related overrides that would also redirect billing away from the subscription.
  delete env.ANTHROPIC_API_URL;
  delete env.CLAUDE_CODE_USE_BEDROCK;
  delete env.CLAUDE_CODE_USE_VERTEX;
  env.CLAUDE_CODE_ENTRYPOINT = 'ground-control-forge';
  return env;
}

lib/generate.js:244–255. The reason is stated at lib/generate.js:238–242 and in CONTRACT-FORGE.md §0b.2: a key present in the parent shell would shadow the OAuth profile and "silently move generation onto metered billing". The contract explicitly instructs "Comment it as such", and the code does. The implementation went further than the contract's three variables and removed three more — an inherited-environment failure that is invisible when it happens, because the run succeeds and only the bill differs. --bare is likewise never passed, with a comment at the argv site saying why (lib/generate.js:677).

Two locks on the same door

Note the tension the comment resolves: --permission-mode acceptEdits is a permissive setting, mandated by CONTRACT-FORGE.md §4's spawn contract, so the deny list is what actually holds. An allowlist alone would depend on the CLI's default-deny behaviour staying default-deny across versions. The contract asked for the allowlist; the implementation added the denylist and explained why in the same breath.

What happens when the subprocess hangs

Any process that shells out to another program has to decide what a hang looks like. Forge gives it 20 minutes, then SIGTERM, then SIGKILL 10 seconds later (lib/generate.js:721–727) — and signals the whole process group, because the child is spawned detached: true:

lib/generate.js:692–695

"Its own process group, so cancel/timeout can signal the whole tree. Without this a grandchild keeps the stdout pipe open after the parent is killed and the job never reaches a terminal state."

The 20 minutes is one of the few numbers in this codebase with a recorded history: "The design-rationale kind reads far more of the repository than onboarding does […] and 10 minutes was cutting long runs off mid-work" (lib/generate.js:29–31). The trade the author accepted is the usual one and is not hedged anywhere: a slow-but-working run and a wedged run are indistinguishable for twenty minutes.

The rule that a rationale document cannot be faked

Forge has two axes — tier (how the document is made) and kind (which document it is) — and exactly one place where they are not orthogonal. The design kind refuses to run on any tier except authored, and returns 400 rather than downgrading:

CONTRACT-FORGE.md §0

"The template tier involves no model at all, and rationale cannot be derived from repository facts — no amount of file-walking tells you why a timeout is 800ms. […] Both fail the same requirement: a rationale document must be able to check its claims against the actual code, because its defining failure mode is inventing a plausible motive, and an invented motive is unfalsifiable."

The onboarding kind falls back to the deterministic tier when the CLI is missing; the design kind has no fallback at all and fails. This is the clearest statement of judgement in the whole repository: a feature that cannot meet its own quality bar is better absent than degraded, because the degraded version of this particular document is indistinguishable from the good one. The implementation matches — lib/generate.js:610 branches on docKind === 'design' for the prompt only, keeping the spawn identical, and there is no design equivalent of lib/artifact-template.js.

The local tier: a measurement that settled an architecture

Stated — CONTRACT-LOCAL.md §0, lib/local.js:8–25

This is the best-evidenced decision in the repository, and the one most worth stealing. The obvious way to add an offline generation tier is to ask a local model for the HTML page. The author tried that, on this machine, before designing anything:

Asked forResult
JSON prose fields, schema-constrainedAccurate. Caught that pandas/matplotlib were declared but unused, flagged a hardcoded key, put three real gaps in unknowns.
The whole HTML artifact, free-formStructurally valid but invented behaviour — claimed a 7-line script doing urlopen + pprint was "cleaning it and preparing it for statistical regression modeling".

Quoted from CONTRACT-LOCAL.md §0. Same model, same input. The contract's own summary: "Constrained mode told the truth; free-form embellished."

The architecture follows directly and is stated as non-negotiable at lib/local.js:8–14: the local model never produces the document. It fills seven bounded prose slots returned as schema-validated JSON; lib/artifact-template.js renders the page exactly as it does for the model-free tier. Every command, path, statistic, tree and heatmap comes from the deterministic brief — "the model is never asked for them, so it cannot invent them". There is no agentic tool loop, because "small models fail worst in that shape".

Then a second layer, for the prose the model does write: CONTRACT-LOCAL.md §3 requires extracting every path-like and command-like token from the output, checking it against the brief and against disk, and dropping the entire sentence containing an unverifiable path rather than silently deleting the token — "because a confident wrong path is worse than a shorter paragraph". The count of dropped sentences is surfaced on the page.

And a finding that inverts the usual instinct: "both models did well on groupStat (12.8 KB brief) and poorly on pitwall (3 KB brief). Brief quality dominates model size — so spend effort on grounding, not on a bigger model" (CONTRACT-LOCAL.md §0). That is why lib/brief.js is the largest module in lib/ at 76.4 KB while the client that talks to the model is 40% of its size.

Decision
Constrain the small model to schema-validated prose slots inside a deterministic template, then verify its output against the filesystem before rendering.
Forces
An 8B local model measurably invents behaviour when given a free-form generative task; offline operation was wanted anyway.
Alternative
Ask for the page and post-process it. Rejected on measured evidence, not on principle.
Consequence
The local tier can only ever produce the onboarding shape, because that is the shape the template renders — which is precisely the reason CONTRACT-FORGE.md §0 gives for refusing to let the design kind use it: "It is the wrong shape and it is blind."

Two constants that must hold a relationship to each other

The scan cache and the process sweep cache are both sized relative to the SSE poll interval, and both fail quietly rather than loudly if the relationship is broken. PROC_TTL_MS (6000) must stay above AGENT_POLL_MS (5000) — "drop it back under 5000 and the cache silently stops working" (lib/agents.js:95–106). CACHE_TTL_MS (30000) must sit comfortably above AGENT_POLL_MS for the same reason (server.js:71–79). The two constants live in different files, are not imported by one another, and nothing asserts the relationship — no test, no runtime check. Someone tuning the poll interval to 8 s to reduce load would silently restore the 226 ms-per-poll behaviour these comments were written to prevent, and no test would fail.

The 800 ms debounce is specified but never justified

CONTRACT.md §2 fixes the value — "debounce 800 ms, re-scan, then emit" — and server.js:268 implements it. Three separate comments reference it as "the existing 800 ms debounce" when reusing it for agent and Forge events. No document, comment or measurement in this repository explains why 800 and not 200 or 2000. It is a specification, not a rationale, and the difference matters: every later change treats it as settled because it appears in a contract.

Invariants: what the code enforces, and what it merely assumes

The assumed ones are the interesting ones

Enforced, with a mechanism you can point at:

  • No path escapes its root. resolveInside throws PathError (403); every file-reading route and the editor launcher call it, and lib/editors.js:9–12 re-checks containment after the caller has already done so, "so a mistake upstream still cannot launch an editor outside the root".
  • Credentials are never read. isSensitive() gates every file read in lib/brief.js and is "deliberately broad: a false positive costs us one TODO sample, a false negative leaks a credential" (lib/brief.js:51–55). A test builds a fixture with a .env, a creds.py and a .pem and fails if the secret value appears anywhere in the brief.
  • Nothing is deleted. One fs.rm in the codebase, reachable only after a verified cross-volume copy; no bulk endpoint; no keyboard shortcut; confirmation requires typing the folder name exactly (lib/reclaim.js:974).
  • Invalid HTML is never staged as success. validateHtml() checks size, <title>, <style> and the absence of any external reference before a job can reach done; failures keep the raw output at <jobId>.raw.txt (lib/generate.js:279–290).
  • Tests cannot touch real projects. fixtureRoot() throws if the path it created is not under the OS temp directory (test/helpers.js:22–24) — the right guard for a suite that exercises a Trash operation.

Assumed, with nothing enforcing it:

  • The cache-TTL ordering above. Documented in prose in two files, checked nowhere.
  • Forge's own subprocess is excluded from the agent sweep. excludePids: generate.forgePids() is passed at four call sites; miss one and Ground Control reports itself as the user's agent — which also makes the project un-trashable, since agent-running is a blocker. The pid is registered "before any await so an agent sweep racing the spawn cannot see this process without knowing it is ours" (lib/generate.js:701–703), which closes the race but not the missed-call-site case.
  • Everything interpolated into generated HTML is escaped. lib/artifact-parts.js:1 states the rule in capitals as "non-negotiable", and it is enforced by convention plus one hostile-content test — not by types or by a template engine that escapes by default.
  • The scanned root contains projects, not one giant repository. Reclaim checks this explicitly with not-a-direct-child and inside-other-repo hard blockers; the scanner does not.

Where the design is under strain

Places the recorded reasoning no longer matches the code

The append-only rule protects working code and does nothing for prose. Four of the five items below are the same failure: a rule changed, and the sentence describing the old rule stayed.

Reclaim's module header describes a rule the module no longer has

The docblock at lib/reclaim.js:18–22 reads: "BLOCKERS ARE HARD REFUSALS. A non-empty blockers array makes removal impossible. trashProject() re-runs the assessment at call time and refuses on any blocker." The code at lib/reclaim.js:967–971 does something else:

  if (soft.length && opts.force !== true) {
    throw new ReclaimError(409, 'this project has blockers that must be overridden explicitly', {
      blockers: soft, hardBlockers: [], softBlockers: soft, overridable: true, assessment,
    });
  }

Only three codes are in HARD_BLOCKERS (lib/reclaim.js:372–376): is-ground-control, not-a-direct-child, inside-other-repo. Everything else — uncommitted changes, unpushed commits, no remote, stashed work, a running agent — is a soft blocker liftable with force: true. CONTRACT-RECLAIM.md documents the new model and keeps the old one under a heading marked "Original note", which is honest but leaves two contradictory tables in one file. README.md:133 still describes the old behaviour: "Removal is refused outright — not warned about". The safety story is unchanged (the destination is still the Trash, every override is logged with the codes it lifted), but a reader who trusts the docblock will believe a running agent makes removal impossible, and it does not.

The Workbench contract contradicts itself in the same file

CONTRACT-WORKBENCH.md §3a introduces POST /api/agents/stop and explains its four guards. Eighty lines later, CONTRACT-WORKBENCH.md:183–184 still states, in bold: "Never kill or signal an agent process. Ground Control observes; it does not manage. No endpoint may terminate a PID." README.md:119 repeats the old claim as well. The code implements §3a.

The scan cache TTL diverged from its specification, with a reason

CONTRACT.md §2 says "serve /api/projects from cache when it is < 5 s old"; README.md:198 says "Results are cached 5s". The code uses 30 s and carries the eight-line comment quoted earlier explaining exactly why 5 s was wrong once the agent poller existed. This is the healthy version of drift — the implementation won on measured grounds and wrote down why — but nothing propagated it back, so the contract now understates the staleness a client may see by 6×.

A safety test asserts on source text, not behaviour

  const src = await import('node:fs').then((fs) =>
    fs.readFileSync(new URL('../lib/agents.js', import.meta.url), 'utf8'));
  assert.match(src, /ACTIVE_WINDOW_MS/, 'the recency window must exist');
  assert.match(src, /a\.live > 0 && a\.active > 0/,
    'state "working" must require BOTH a live process and recent transcript activity');

test/safety.test.js:78–83. The regression it guards is real and documented right above it (12 of 13 processes reported as "working" with transcripts last written 23–62 hours earlier). But the assertion passes if ACTIVE_WINDOW_MS is changed to 60 hours, and fails if the expression is reformatted across two lines. It pins the source, not the property.

Two directory walks, two orders, one explanation

lib/brief.js:122–126 explains its queue-based traversal at length: "Breadth-first on purpose. A depth-first walk of animAgent burns the entry budget inside its 19k-file fixture tree and never reaches Sources/, which silently loses the real entry points." lib/scan.js:97–99 walks with stack.pop() — depth-first — under a 20,000-entry budget, half of brief.js's. Inferred The consequence differs (scan needs counts, not entry points, so truncation costs accuracy rather than correctness) and that may be exactly why the author did not change it — but nothing says so, and the two files sit two directories apart with the hazard explained in only one of them.

A smaller one: the shedding notes describe the plan, not the reality

Each budget level in lib/brief.js:1446–1465 carries a fixed dropped string. The brief that produced this document reported "design evidence trimmed: 4 documents, 40 comments, 15 commit bodies" — in a directory that is not a git repository and has no commit bodies at all. The note describes the cap that was applied, not what was actually lost, in a section of the brief headed "What this brief could NOT determine".

What this design costs

Unsentimental

  • It is macOS-only, structurally. Not by configuration — by mechanism. ps -ax -o ... comm= and lsof -Fn for agent detection, ~/.Trash plus fs.rename for Reclaim, open -a for every editor, sips/iconutil for the icon, AppKit and WKWebView for the shell. Porting is not a compatibility layer; it is a rewrite of four modules.
  • It scales to a folder, not to a fleet. Every request re-walks the filesystem; there is no index and no persistence. The stated numbers — a full scan of 19 projects in ~0.55 s, ~800 ms with agents — are the operating point the caches were tuned around. Two hundred projects would multiply the walk, the per-project git subprocesses, and the lsof-per-pid step together, and the 1.5 s agent budget would be exceeded on every scan rather than never.
  • The frontend cannot be split. 169 KB of app.js and 183 KB of CSS ship as-is, ungzipped by the server, on every load. That is fine over loopback and would be indefensible anywhere else — which is a coherent position for a localhost tool, provided nobody later wants it to be anything else.
  • Forge is coupled to one CLI's surface. Nine argv flags, a stream-json event schema, a result event's field names, and a rate-limit event shape. The parser skips malformed lines rather than failing, so a schema change degrades to a job that produces no progress and then no artifact.
  • The design-kind guarantee is absolute in the unhelpful direction. No claude CLI means no design document, ever, with no partial fallback. That is the stated intent, and it is the right call for correctness; it also means the feature is unavailable exactly when the machine is offline, which is when a local dashboard is most likely to be the only tool you have.
  • Nothing keeps six contracts, one README and a dozen module docblocks in agreement. The prose is the specification and there is no test that reads it. The drift catalogued above is the ordinary cost of that, and it will grow.

What to take from this, and what not to

Measure before you architect, and write the measurement down. The strongest decisions here are not the clever ones; they are the ones with a number attached. "Seven processes with nothing written for two to three days" produced the 90-minute parked window. "226 ms per poll versus ~0 ms on a hit" produced a 6 s cache TTL. "The same model invented behaviour when asked for HTML and told the truth when asked for JSON" produced an entire tier's architecture. Each of those comments will still be legible to someone changing the value in two years, which is the only test a rationale comment has to pass.

Put an unfalsifiable failure mode behind a hard refusal. Forge falls back for onboarding documents and refuses outright for rationale documents, because a wrong command announces itself and a wrong motive does not. Generalised: when the degraded output of a feature is indistinguishable from the good output, "unavailable" is a better state than "degraded", and it should be enforced at the API rather than left to the UI.

Keep a dangerous capability out of the module that claims not to have it. lib/agents.js can be shown to be observe-only by reading one file, because the single process.kill lives in the HTTP handler instead. A property that can be checked locally is worth more than the same property distributed across a boundary.

What not to copy. The zero-dependency rule bought real things here — offline operation, a two-line install, a small audit surface — and it is affordable because the domain is small and the security posture is "treat every file as hostile", which a from-scratch renderer expresses more directly than a configured one. In a codebase with a wider surface, hand-writing a markdown parser is a liability, not a virtue. Likewise the append-only contract discipline: it exists to let authors who cannot talk to each other work in parallel, and it produced two files that can no longer be reorganised. If your authors can talk to each other, you are paying that price for nothing. And the ~7 GB of free disk that settled Electron versus Swift is a fact about one laptop, not an argument.
