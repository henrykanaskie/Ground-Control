The one fact that shapes every file

There are no third-party packages. package.json declares no dependencies and no devDependencies block at all; every import in lib/ and server.js is either a node: builtin or a relative path to another file in this repository. The browser code imports nothing. So "which library does this?" almost always has the same answer: it does it itself, in a function you can open.

What is actually in here

Orientation

Four kinds of code share this repository, and they follow different rules. The Node server and lib/ are one dialect. The browser bundle in public/js/ is a second, written against the DOM with no build step. app/GroundControl.swift is a native shell, and build-app.sh assembles it.

  • JavaScript 80% · 2.5 MB
  • CSS 9.8% · 317 KB
  • Markdown 4.1% · 135 KB
  • HTML 3.4% · 111 KB
  • Swift 1.8% · 58.5 KB
  • Shell 0.3% · 8.4 KB

Roughly half of that JavaScript total is not source you should read. GroundControl.app/ and Vantage.app/ are built application bundles checked into the repository, each carrying its own frozen copy of server.js and lib/. When a search returns three hits for one function, two of them are usually those copies.

Where to start reading

lib/util.js is imported 21 times, more than any other internal module, and it is short. Read it first: it holds the ignore list, the slug rules, the relative-time formatter, the MIME table and resolveInside, the path guard every file-reading route depends on. After that, lib/git.js at 194 lines is the cleanest example of the house style.

The shape of a typical file

lib/git.js, top to bottom

  • ES modules
  • named exports at the bottom
  • jsdoc block comments
  • promise wrapper

Every module in lib/ that does work (as opposed to rendering HTML) has the same five-part skeleton. Learn it once and the other sixteen files stop being unfamiliar.

1. Header
A block comment naming the module and stating its rules. In lib/git.js the header is three sentences and it tells you the whole contract: argv arrays, no shell, a 5 second timeout, failures resolve to null.
2. Imports
Builtins first with the node: prefix, then relative imports of project files, always with the .js extension. There is no bare-package import anywhere.
3. Constants
SCREAMING_CASE at module scope, each with a comment saying what the number protects. GIT_TIMEOUT_MS = 5000, MAX_BUFFER = 32 * 1024 * 1024.
4. Functions
Plain function declarations, not arrow constants. Sections are separated by a banner comment of dashes. Small helpers sit next to the code that uses them.
5. Exports
One export { … } block on the last line. Nothing is exported inline.

The one function to read closely is the wrapper every other function in the file calls. It shows the error convention, the subprocess convention and the promise convention in eighteen lines.

Because failure is null rather than an exception, the caller can fire seven git commands at once and let each one fail on its own. Promise.all here is not a fan-out over unreliable work that might reject; every entry is guaranteed to settle.

One more idiom appears at the top of nearly every file that consumes another module. The import brings in the whole namespace, then a destructuring assignment lifts out the handful of names the file actually uses.

One request, all the way down

GET /api/projects

This is the operation the whole project exists to perform: turn a list of folders into the payload that draws the grid. Follow it once and most of server.js and lib/scan.js become readable.

The cache at the top of that flow carries the most interesting comment in the server, because the number in it was chosen against a measurement rather than a preference.

The SSE stream polls for agent activity every 5 seconds, and each poll calls getScan(false). What happens if you set the scan cache TTL to something near 5 seconds so the dashboard stays fresher?

It gets slower, continuously. The comment at server.js:162 records the measurement: a full scan takes about 800ms, so a TTL near the poll interval "lands the freshness check on alternating sides of the boundary and triggers a synchronous 32k-dirent re-walk every ~10s even when nothing on disk changed". The fix was to move the TTL well clear of the poll interval, to CACHE_TTL_MS = 30000, and let the paths that genuinely need freshness pass fresh=true.

The same shape appears in lib/agents.js:89, where PROC_TTL_MS = 6000 must sit above the same 5 second poll: at 2500ms the cached process sweep had always expired by the next poll, so every poll paid a full ps plus lsof, measured at 226ms of work and roughly 4 to 5% of a core at idle.

The walk at the far end of that chain is the only place this project reads a directory tree, and it is written as an explicit stack rather than recursion so that its budgets are enforceable. Every limit is a named constant at the top of lib/scan.js.

The constructs this code leans on

Language features, in context

The JavaScript here is modern but deliberately plain. There are no generators, no Proxy, no decorators, no class hierarchies: the four classes in the codebase (PathError, Marks, Registry, SourceError) each extend nothing or extend Error. What the code does lean on is listed below, each with a real site.

  • async / awaitEverywhere I/O happens. Every async function that can fail returns a value rather than throwing.lib/scan.js:260
  • Promise.allFan out independent work and wait once. Used only where each promise is already failure-proof.lib/git.js:74, lib/scan.js:469
  • optional catch bindingcatch { } with no error variable. The dominant error idiom in this repo: swallow, degrade, carry on.lib/scan.js:103
  • destructuringOn imports, on Promise.all results, and on split lines: const [, iso, subject, author] = headRaw.split(SEP).lib/git.js:93
  • spread / restMostly to turn a Map or Set into a sortable array: [...langBytes.entries()].lib/scan.js:205
  • template literalBoth for short strings and, in lib/house-style.js, for multi-thousand-line prompt documents.server.js:408
  • Map / SetThe default containers. Set for ignore lists and dedupe, Map for every registry.lib/util.js:13, lib/comms.js:76
  • EventEmitterNode's publish/subscribe object. Two registries use one, and both hand back an unsubscribe function.lib/jobs.js:21, lib/comms.js:80
  • AbortControllerThe standard cancellation handle. Used where there is no subprocess to signal, notably the local HTTP tier.lib/generate.js:652
  • SymbolExactly one, as a sentinel value that cannot collide with any real result. See the race below.lib/agents.js:787
  • sticky regex stateA /g regex keeps a lastIndex between calls, so module-level ones are reset before use.lib/scan.js:187
  • createElementNSBrowser side only. SVG nodes must be created in the SVG namespace or they render as nothing.public/js/app.js:24

Two of those deserve the code rather than a description. The first is the sentinel, which solves a problem Promise.race creates: the race tells you which promise won, but if the winner's value could itself be null or an empty array you cannot tell a timeout from an answer.

The second is the error idiom that appears more than any other construct in the repository: a try whose catch takes no argument and does nothing but continue.

The absence is as much a decision as the presence, and it is a decision with a visible bill: public/js/markdown.js is a 49.8 KB markdown renderer and lib/artifact-parts.js is a 53.3 KB HTML component library, both written from scratch.

Why no dependencies at all, not even one?

What it does

package.json declares no dependencies, so node server.js runs a fresh clone with no install step, and the browser loads two hand-written ES modules with no bundler.

What else was on the table
  • expresswould have replaced roughly 80 lines of route() and sendJSON, and given body parsing for free. It also adds a dependency tree to a tool whose whole selling point is that it reads your projects and installs nothing.
  • marked or markdown-itwould have deleted public/js/markdown.js entirely, at the cost of auditing someone else's sanitiser for a renderer that is deliberately fed hostile input from disk.
  • simple-git or nodegitwould have removed the format-string parsing in lib/git.js, but the parsing is 40 lines and a native binding would break the "clone and run" property on every Node upgrade.
What tipped it

The repository states the constraint rather than the motive: server.js:7 says "Node stdlib only", every lib/ header repeats it, and the README puts "No dependencies. Node standard library and vanilla browser JS" in bold. Nothing records a deliberation, so read it as a hard requirement the code was written to satisfy, not as a conclusion someone reached.

What it costs you

About 100 KB of hand-written renderer and component code that you now own, including its security posture. Every markdown edge case is your bug. If the artifact HTML needed a real templating language, or the dashboard needed reactive state, you would be writing the third and fourth of these libraries rather than the first two. The break-even point is somewhere just past where this project is now.

Three ways to start a process

node:child_process, in detail

Nineteen imports of node:child_process make it the most used builtin after fs and path, and the project picks a different entry point for each of three jobs. Knowing which one to reach for is most of writing new code here.

CallWhereWhy that one
execFilelib/git.js:32, lib/agents.js:126, server.js:628 Short command, output collected in one buffer, hard timeout. Nothing streams.
spawnlib/generate.js:824, lib/comms.js:347 Long-running claude process whose stdout is read line by line for minutes, and whose stdin receives the prompt.
spawnSynclib/generate.js:261 One-shot claude --version probe during a status check, cached 60 seconds.

The spawn case is where this codebase does something worth studying. Both lib/generate.js and lib/comms.js run the authenticated claude CLI as a child process and read its stream-json output, and both carry the same three unusual decisions: a stripped environment, an argv-level permission fence, and a detached process group.

The environment handed to that child is not the server's own. Three variables are deleted before the process starts, and the comment above the function explains exactly what would break otherwise.

Why shell out to a CLI instead of calling the API over HTTPS?

What it does

Forge and Comms both locate a claude executable on PATH (lib/generate.js:235, with four extra candidate paths), spawn it, write the prompt to its stdin, and parse newline-delimited JSON events off its stdout.

What else was on the table
  • An HTTPS call to the APIwould need a key, which means asking the user for one, storing it, and billing them per run. It would also mean reimplementing the agent loop: the tool calls that let the model read the repository are the entire point of the authored tier.
  • An SDK dependencywould break the no-dependency rule and still need the key.
  • No model at allis a real option and is shipped: the template tier renders the artifact from the deterministic brief with no model involved (lib/generate.js:590).
What tipped it

Stated, in the module header at lib/generate.js:7: "this machine has no ANTHROPIC_API_KEY; the CLI is authenticated against a Claude Max subscription". The billing constraint is written down; the choice follows from it.

What it costs you

A process boundary with a protocol on it. Roughly 400 lines of lib/generate.js exist only to manage that boundary: locating the binary, buffering stdout into lines, distinguishing a timeout from a cancel from a usage limit, reaping grandchildren, and validating that the bytes coming back are really an HTML document. The output is also unstructured text that has to be sanitised and validated (lib/generate.js:310 and :327) rather than a typed response.

That boundary has one genuinely tricky part, and it is the sort of thing that only shows up in production: knowing when the child is finished. Node gives you two events and neither one alone is correct.

The same file also shows how the child is stopped. detached: true puts the child in its own process group, and process.kill(-pid, …) with a negative pid signals that whole group, which is how a Bash call's leftovers get cleaned up too.

The stop path, and its fallback lib/generate.js:867 
  /** Signal the child's whole process group, falling back to the pid alone. */
  function stop(signal) {
    state.killed = true;
    try { process.kill(-child.pid, signal); }
    catch { try { child.kill(signal); } catch { /* already gone */ } }
  }

The negative pid is the group. If the platform refuses it, the fallback signals just the child. Cancellation, the 20 minute timeout and server shutdown all funnel through this one function; jobs.setCanceller (lib/jobs.js) is how the HTTP layer reaches it without ever seeing a pid.

Comms builds its argv the same way, and its one non-obvious flag carries a comment explaining why it can never be omitted.

How errors travel

The convention that is not a language feature

This codebase almost never throws across a module boundary. Read any function asking "what does this return when the disk lies to me?" and the answer is nearly always a value: null, an empty array, or a filled-in object with a scan failed label on it.

  • Degrade field by field. gitlib.summary returns an object where each field independently falls back, because each came from its own git call that resolved to null.
  • One bad item must not sink the batch. lib/scan.js:354 wraps each document in its own try, with the comment "one bad doc must not sink the project"; the same shape guards each project inside scanSources.
  • The process never dies. server.js:40 installs handlers for uncaughtException and unhandledRejection that log and continue.
  • Errors that must reach the user carry a status. Where a failure is the user's business, the code attaches one: Object.assign(new Error('unknown chat'), { status: 404 }) in lib/comms.js:261, or a custom class such as PathError (lib/util.js:240) whose constructor sets this.status = 403.

The exception that proves the rule

There is one place where a failed write deliberately aborts everything. lib/reclaim.js:1028 writes an audit line before moving a folder to the Trash, and if that write fails it throws: "the reclaim log could not be written, so nothing was moved". Everywhere else, logging is best-effort. Here the record is the feature, so no record means no action.

Async cleanup follows a matching convention: any subscription hands back a function that cancels it, and the caller keeps that function rather than an id.

The guards, and where they live

Path safety, privacy caps, refusals

This server reads arbitrary folders on the machine and hands their contents to a browser, so the checks are not incidental. Three of them appear over and over, and new code that touches a file or a route is expected to use them.

The second guard is a network one. The server binds every interface, so anyone on the network can look at the dashboard; the routes that change what it watches, or that start an agent, check where the request came from first.

GuardSiteWhat it refuses
resolveInsidelib/util.js:256 Any ?path= that escapes the project, including through a symlink. Used by /api/doc, /api/raw and the static handler.
isLocalRequestserver.js:2037 Adding or removing a watched folder, browsing the disk, and every Comms route, from anywhere but loopback. Handles ::ffff:127.0.0.1, the dual-stack form.

Note the shape shared by all five: an allowlist or a refusal, expressed as a small pure function in a module, called at the edge. None of them is inline in a route handler.

Reading a file you must not read whole

lib/agents.js and its budgets

Agent detection is the most constrained code in the repository, and it is a good study in writing against real numbers. It answers "is a coding agent working in this folder right now" from two sources that are both expensive: the process table, and session transcript files that reach 9 MB.

A claude process is running, and its transcript file was written to fifteen seconds ago. Is an agent working in that folder?

No, and this was a real bug fixed by commit cd994f9. A session that finished replying thirty seconds ago has a fresh modification time and is doing nothing at all. Liveness is not the signal and recency is not the signal either; the signal is the shape of the last event in the transcript.

turnStateOf (lib/agents.js:722) scans backwards through the parsed events: a trailing tool or user event means the turn is still in flight, and a trailing assistant event means the model replied and stopped. Two more bounds sit on top of it: OPEN_WINDOW_MS (90 minutes) below which a live process counts as present at all, and STALL_WINDOW_MS (10 minutes) after which a session stuck mid-turn stops claiming to be busy, because a process killed during a tool call leaves a tool event as the last thing ever written.

Those constants are the decision, so they are documented like one. Every budget in that file carries a comment giving the measurement behind it, which is the convention worth carrying into new code here: a number without a reason will be changed by someone who does not know what it protects.

Things that will confuse you

The traps, with their explanations

Five things in this repository look wrong until you know why they are there. Two of them are artefacts of the tooling rather than the code.

An automated scan of this repository reports a third-party library named y, imported nine times. There is no such package. Where does it come from?

From a comment, matched by the very regular expression the comment describes. lib/brief.js:722 introduces the import-detection patterns with the example line // JS/TS: import x from 'y' / import 'y' / export … from 'y', and the pattern on the next line matches that comment text. Three matches per file, and the file exists three times (the source plus the two checked-in .app bundles), which is the nine.

The same effect explains "async iterator (for await)" appearing in the construct table. lib/house-style.js:1368 mentions for await (const chunk of stream) inside a prompt string, and that is the only occurrence in the entire repository: a search for real for await loops in lib/, public/ and server.js returns nothing else. The lesson generalises: this project's scanner reads strings and comments as code, so treat its output as coordinates to check, not as facts.

Looks likeActually is
Duplicate source files. Three copies of brief.js, two of server.js. GroundControl.app/ and Vantage.app/ are built bundles committed to the repository. Their Contents/Resources/ holds a frozen copy of the source at build time. Edit the root copy; the bundle is regenerated by build-app.sh.
A stale environment variable. VANTAGE_OLLAMA_HOST is read somewhere but appears nowhere in lib/. It lives only in the older Vantage.app bundle. The live code reads GROUND_CONTROL_OLLAMA_HOST then OLLAMA_HOST (lib/local.js:42).
A Map with properties on it. agentActivity returns a Map, then sets map.budgetExceeded. Deliberate, via Object.defineProperty(…, { enumerable: false }) at lib/agents.js:774, so the flags ride along with the result without appearing as entries when the Map is iterated.
A cache being patched by hand. marksChanged() reaches into cache.payload and mutates it. server.js:110 explains it: marking a project complete flips one boolean on one project, and "a full re-walk to flip one boolean is pure waste". Invalidating the cache would cost an 800ms rescan per click.
A regex that is reset before use. TODO_RE.lastIndex = 0 before the loop. A regex literal with the /g flag stored at module scope keeps its lastIndex between calls. Without the reset, the second file scanned would start matching from wherever the first one stopped (lib/scan.js:187).

One more, on the browser side. public/js/app.js is 234 KB of vanilla DOM code and it builds every node by hand, which looks verbose until you notice the rule it is enforcing.

How the tests are written

node --test, 9 files, no framework

The suite runs with npm test, which is node --test test/*.test.js. Every test imports test from node:test and assert from node:assert/strict, builds its fixtures in a temporary directory, and registers test.after(cleanupFixtures).

One category of test here is unusual enough to point out: several assertions read a source file as text and match a regular expression against it. That is normally a smell, and the comments explain why it is used deliberately.

The rest of the suite is conventional, and weighted toward what would be expensive to get wrong: every blocker that prevents a folder being trashed has a fixture, path traversal is asserted on every file-reading route, and a fixture repository containing a fake credential is briefed with the test failing if the secret value appears anywhere in the output.

Writing code that fits

A short close

If you are adding a feature, the fastest route is to copy a shape that already exists rather than to invent one.

  1. A new derived fact about a project goes in lib/scan.js, into the accumulator inside walkProject if it needs the file walk, and then onto the base object in scanProject. Add it to failedProject too, so the shape stays complete when a scan fails.
  2. A new external command goes through execFile with an argv array, a timeout, and a promise that resolves null on failure. Copy git() from lib/git.js:27 or run() from lib/agents.js:120.
  3. A new route is a string comparison inside route(). If it is not a GET, dispatch it before the read-only method guard at server.js:561 and check the method inside your own handler, which is what every existing feature block does.
  4. Anything that reads a file the user named calls resolveInside(project.path, rel) and returns 403 on PathError. Anything that changes state or starts a process also calls isLocalRequest(req).
  5. A new module gets the five-part skeleton: header comment stating its rules, imports, named constants with reasons, functions, and one export { … } block at the bottom.

And the four things that would mark new code as foreign here, in rough order of how quickly someone would notice:

Instead ofDo what the codebase does
Adding an npm dependencyWrite the twenty lines, or ship the feature without it. There is no precedent for the first option anywhere in the tree.
Throwing an error up through a moduleReturn null or a filled-in fallback, and attach a status only where the user must see it.
exec with an interpolated command string execFile or spawn with an argv array. There is no shell in this codebase and no reason to add one.
A bare number in a conditionA named constant at the top of the file with a comment saying what it protects and what breaks if it is wrong.
innerHTML in the browser codeh() and textContent. The one exception is the markdown reader, and it is documented as such at the top of public/js/app.js.

What to take away

The consistency here is the point. One error convention, one subprocess convention, one export convention, one path guard, and a comment above every number explaining what it protects. That makes an unfamiliar file in this repository predictable: you can guess where the constants are, guess that a failure returns a value, and guess that the exports are on the last line, and you will be right.

The two things worth carrying elsewhere are smaller than the architecture. First, a budget with a measurement in its comment survives contact with the next maintainer; a bare number does not. Second, when a flag or a call is deliberately absent, say so in a comment where the flag would have gone, because absence leaves no other trace.
