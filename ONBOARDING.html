Read the author's own prose first

README.md (2,782 words) is accurate and unusually good: it explains every feature and most of the reasoning. This document does not repeat it. It gives you the parts the README does not: how the mechanisms actually work, what the decisions cost, where the code and the README disagree, and what to touch first. The ten CONTRACT*.md files are the specs the features were built against, and they are still the reference for API shapes.

What it is, and what it is not

Scope

You give it a list of folders. Each folder is either a shelf of projects (every child directory becomes a card) or one project (the folder itself is a card). It walks each project once, reads git, picks the project's best documentation, and renders a grid you can filter and sort. Click a card and you get a commit heatmap, the file tree, the documents rendered in a from-scratch markdown reader, live agent activity, and a chat that starts a real Claude Code agent in that folder.

It is not a CI dashboard, not multi-user, and not portable. It shells out to ps, lsof, osascript, open and ~/.Trash, and it parses BSD ps time formats (lib/agents.js:165). It will start on Linux and most of the read paths will work, but agent detection, Reclaim and the folder picker are macOS code. Nothing about it is designed to be deployed.

Getting it running

Ten minutes, no install step

There is nothing to install. package.json declares no dependencies and no devDependencies; it declares "engines": {"node": ">=18"} and "type": "module". Clone it, have Node 18 or newer, run one command. On a first run with no config, it starts on ~/coding_projects and opens a browser at http://localhost:7377.

The happy path is implied, not proven here: I read the code but did not run the server or the test suite while writing this. The README states the suite is 99 tests running in about 5 seconds; test/ holds eight *.test.js files plus helpers.js, and a rough count of test( calls across them is closer to 120, so treat the README figure as approximate.

How it is put together

One process, four boundaries

One Node process serves everything: the static files, the JSON API, and a Server-Sent Events stream. The browser side is a single 234 KB ES module with no framework. The interesting structure is not the module list, it is the four places this process reaches outside itself: your project folders (read), Claude Code's transcript store (read), the claude binary (spawned), and its own config directory (written).

Dependencies point one way: server.js imports every lib module; lib modules import lib/util.js, lib/git.js and lib/docs.js and nothing above themselves. The one exception is deliberate: lib/generate.js loads house-style.js, local.js and artifact-template.js with lazy dynamic import() wrapped in .catch(), so a missing or broken module degrades one tier instead of failing at import time (lib/generate.js:48).

Mechanism: how a folder becomes a card

lib/scan.js

The obvious implementation is to stat the folder and use its modification time. That fails twice over. A fresh git clone has today's mtimes on every file and is not active work; and a directory's own mtime moves when Finder merely looks at it. So the scan derives "last activity" from whichever signal is actually trustworthy for that project's state.

The walk itself is one pass with hard budgets: depth 6, 20,000 dirents, at most 600 files opened for TODO markers and never a file over 512 KB (lib/scan.js:25). It follows symlinks only far enough to classify them and keeps a set of real paths so a symlink loop cannot spin. Nothing in it throws: unreadable entries are skipped, and a project whose walk blows up entirely still returns a complete summary built from git alone.

Follow one real project all the way through

Trace this repository itself. scanSources iterates the registry, and for the root source ~/coding_projects it lists child directories, dedupes on fs.realpathSync, and assigns ids alphabetically with uniqueSlug, so ground-control keeps its id no matter what is added later. Then, for this folder:

  • walkProject counts 101 files, 5.4 MB, and records language bytes: JavaScript wins, so primaryLanguage is JavaScript.
  • markerFor sees package.json and adds the marker Node; buildStack folds in the loudest languages, giving ["Node", "JavaScript", "CSS", "Markdown"].
  • The repo is clean, so lastMs is the last commit; commitsLast7d is 3, so statusReason reads "3 commits this week" and the dot is active.
  • pickFeatured finds no ONBOARDING, no CLAUDE.md, and takes the best root-level document by kind: README.md.
  • blurbFromMarkdown skips the # heading and returns the first real paragraph: "A live dashboard over the projects you point it at, and a place to work from, not just look at."

That last string is checkable: it is the description this repository's own tooling extracts for itself. I traced these steps by reading the code, not by running the scanner.

The lesson

When a cheap signal is right most of the time and catastrophically wrong the rest, do not add a fudge factor to it. Ask what state the thing is in first, and pick a different signal per state. Three named branches beat one clever heuristic.

Mechanism: is an agent working in this project right now?

lib/agents.js, the most carefully argued file in the repo

This is the feature the author spent the most care on, and the comments record why. The naive version is one line: find a claude process whose working directory is inside the project. That version was built, shipped, and found to be wrong in three separate ways, each of which is now a named guard.

There is a live claude process whose working directory is inside a project you watch. Is an agent working in that project?

Usually not. The comment at lib/agents.js:58 records the measurement: seven processes on the author's machine had a cwd set and had written nothing to their transcripts for two to three days, one for six. They were editor tabs left open, not work. A live process proves a session exists, not that anything is happening in it.

So the process is only half the evidence. The other half is the transcript: if nothing has been written to it in 90 minutes the process is reclassified as parked and stops counting as presence, and even a fresh transcript only means "working" if its last event is the right shape.

Three more details are load-bearing. The sweep reads comm rather than command, because a real install path contains spaces and the launcher would be counted twice (lib/agents.js:176). Transcript directories are resolved for the project root and every live process's cwd, because Claude Code keys its store on the session's cwd, so an agent working in a subfolder writes somewhere else entirely (lib/agents.js:414). And the PIDs of Forge's and Comms' own children are excluded, or Ground Control would report itself as your agent (server.js:1188).

The agent poller runs every 5 seconds and the process sweep is cached. Why is that cache 6 seconds and not 3?

Because a TTL below the poll interval means the cache has always expired by the time the next poll arrives, so it never hits. The comment at lib/agents.js:89 records the measurement: at a 2,500 ms TTL every single poll paid a full ps plus lsof sweep, 226 ms of work against roughly zero on a hit, burning about 4 to 5 percent of a core continuously while idle.

PROC_TTL_MS = 6000 carries one poll's sweep to the next with margin for tick jitter. This is an invariant between two constants in two different files: PROC_TTL_MS in lib/agents.js must stay above AGENT_POLL_MS in server.js. Nothing enforces it and no test covers it. The same relationship holds for the scan cache: CACHE_TTL_MS is 30,000 for the same reason.

The lesson

A signal that can be wrong needs a second, independent signal, not a more careful reading of the first. And when you add a cache in front of a poller, the two intervals become a pair: write the relationship down next to both numbers, because the failure mode is a silent performance regression, not an error.

Mechanism: Forge, and the gate that counts

lib/brief.js, lib/house-style.js, lib/generate.js

Forge writes a project's onboarding document. The naive shape is "send the repository to a model and save what comes back". What actually happens splits that into a part with no model in it at all and a part where the model is constrained on both ends: it is given facts it did not gather, restricted to three read-only tools, and its output is measured before it is allowed to become an artifact.

The most interesting gate is the last one, and the comment above it is a confession. The prompts had asked for diagrams "since the beginning", and a real generated artifact still came out at 3,810 words with none. So the code stopped asking and started counting.

The lesson

Asking harder is not a mechanism. If a quality bar matters, something in the pipeline has to measure it and be able to say no; and when you write that gate, calibrate it against the specific artifact that failed, not against an idea of quality.

The decisions, and what they cost you

Four forks in the road

These are the choices you will have to live with or unpick. Where the repository states a reason I have quoted it; where it does not, I say so and give the trade-off as analysis rather than as the author's thinking.

Why no dependencies at all, not even Express?

What it does

Everything is Node's standard library and vanilla browser JavaScript. package.json lists no dependencies, there is no bundler, and the front end is loaded as a plain ES module.

What else was on the table
  • Express + chokidaryou would delete maybe 200 lines of routing and the fs.watch wrapper, and gain a node_modules that this tool would then have to teach itself to ignore.
  • React or Svelte + Vitethe grid diffing in syncCards and the whole detail view would be framework-shaped instead of hand-written, at the cost of a build step between editing a file and seeing it.
  • marked or markdown-itwould replace 49.8 KB of hand-written renderer, and would need its own XSS review, since every document rendered here is untrusted input.
What tipped it

Stated, and treated as a hard rule for every contributor: CONTRACT.md:15 reads "Node.js stdlib ONLY. No npm installs, no package.json dependencies, no CDN links, no external fonts. The whole thing must run offline with node server.js." The macOS bundle depends on it too: build-app.sh copies four paths into the app and deletes any node_modules it finds.

What it costs you

A 234 KB front-end file with no module boundaries and no tests, a markdown renderer you now own the security of, and a hand-rolled SSE reconnect. Every browser-side bug is yours to fix. The upside is real and unusual: clone and run, no lockfile drift, nothing to audit, and it works with no network.

Why shell out to the claude CLI instead of calling the API?

What it does

Forge and Comms spawn the user's own authenticated claude binary in headless mode (-p --output-format stream-json) and parse its event stream. childEnv() deletes ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN, ANTHROPIC_BASE_URL, ANTHROPIC_API_URL, CLAUDE_CODE_USE_BEDROCK and CLAUDE_CODE_USE_VERTEX from the child environment.

What else was on the table
  • The HTTP API with an API keyno subprocess, no process-group juggling, no orphan reaping, and structured responses instead of a JSON-lines parser. It bills per token and needs a secret stored somewhere.
  • An agent frameworkwould provide the tool loop, and would break rule one: it is a dependency.
  • A local model onlyfree and offline, and measurably worse: see the ollama tier, which exists but is deliberately confined to filling prose slots.
What tipped it

Stated at lib/generate.js:7: "this machine has no ANTHROPIC_API_KEY; the CLI is authenticated against a Claude Max subscription", and the key-stripping exists so a key in the parent shell "can never shadow the OAuth profile and silently move generation onto metered billing". --bare is named as deliberately absent because it forces API-key auth.

What it costs you

A large amount of process plumbing that has nothing to do with the feature: detached process groups, exit versus close races, SIGTERM then SIGKILL grace periods, PID exclusion lists so the agent detector does not report Ground Control's own children, and a pid written to disk so a restart can find an orphan. It also cannot run headless or in CI, because it depends on an interactive login, and the cost figure shown in the UI is a list-price equivalent rather than a charge.

Why does Reclaim move folders to the Trash instead of deleting them?

What it does

The only exit for a project folder is fs.rename into ~/.Trash. There is no rm -rf in the codebase and no permanent-delete option. The single fsp.rm in lib/reclaim.js runs only after a cross-volume copy has been made and verified file-count and byte-for-byte.

What else was on the table
  • Real deletion with an undo logfaster and simpler, and the undo is a promise you cannot keep once the bytes are gone.
  • osascript / Finder automationthe documented way to trash a file on macOS. Rejected in a comment at lib/reclaim.js:24: it "triggers a macOS TCC prompt that hangs a headless server indefinitely".
  • Report only, never movezero risk and a feature that stops one click short of being useful.
What tipped it

Stated as rule zero of the module: "a false dead verdict is far worse than a missed one." Everything follows: blockers are hard refusals, anything unverifiable (git that will not answer, an agent sweep that fails) becomes a blocker, and trashProject re-runs the whole assessment at call time rather than trusting what the UI sent.

What it costs you

An EXDEV code path with its own copy-and-verify implementation, a Trash that fills up, and refusals that will occasionally block something you genuinely want gone. That last one was later softened: blockers are now split into hard (three: it is Ground Control itself, it is not a direct child of a watched folder, it is inside a larger repo) and soft (everything else), which lift with an explicit force and are recorded by code in .forge/reclaim-log.jsonl.

Why does continuing a chat session always fork it?

What it does

Opening a chat on an existing session passes --resume <id> --fork-session, always. The new session id arrives on the CLI's first event and every later turn resumes the fork, never the original.

What else was on the table
  • Resume in placeone conversation instead of two, and if that session is also open in a terminal you have two processes appending to one transcript file. The comment is blunt: "the loser of that race loses work."
  • Type into the running agentimpossible. A live claude process has no inbox, and the panel says so rather than pretending.
  • Refuse to continue at allsafe, and it throws away the only way to carry existing context into the dashboard.
What tipped it

Stated in the module header and pinned by a test: the suite asserts that --fork-session is in the argv, that later turns resume the fork rather than the original, and that a chat agent is never handed a folder beyond the project it was opened on.

What it costs you

Two diverging conversations that look alike, a transcript store that grows a fork per continued chat, and a subtle mental model to explain in the UI. What you get is that nothing Ground Control does can corrupt a session you have open somewhere else.

Where the state lives

Three JSON files, and one that is not state at all

Almost everything on a card is observed: it is recomputed from the filesystem on every scan and nothing persists it. Exactly four things are remembered, and all four live outside your projects, in ~/.ground-control/ (relocatable with --config or GROUND_CONTROL_CONFIG, which the tests use to stay away from your real list).

sources.json
The watched folders: {id, kind, path, label, addedISO}. Written atomically (temp file, then rename, mode 0600). A malformed file never stops the server; it falls back to the default root and reports the failure.
marks.json
The projects you declared complete. Keyed by absolute path, not project id, because an id is a slug that uniqueSlug can reassign once a sibling of the same name appears.
comms.json
The chat index: ids, titles, session ids, turns as displayed, and the pid of any turn in flight. Debounced writes, except the pid, which is written immediately.
.forge/
Inside the Ground Control checkout, not your home: staged artifacts at .forge/<projectId>/<jobId>.html, the job registry, and reclaim-log.jsonl. Staged files older than 7 days are pruned, and the pruner refuses to run on any directory not ending in .forge.

The choice of format is worth understanding before you change it, because "just put it in SQLite" is the first instinct and it would cost the thing that makes this project run anywhere.

The one destructive path, gate by gate

lib/reclaim.js

Everything else in this codebase reads. This one function moves a folder. It is worth knowing the sequence by heart before you touch anything near it, because several of the steps look redundant and none of them are.

Scoring runs on meaningful content, not raw file counts, and the header records the two examples that forced it: a folder that looks like 11,557 files and 341 MB is almost entirely a virtualenv, and another that looks like 861 files holds exactly one real one. Lockfiles, git bookkeeping, .DS_Store and empty files are all excluded, and the newest-mtime clock ignores them too, because Finder rewrites .DS_Store just for looking at a folder.

If the destination is on another volume, fs.rename fails with EXDEV and the fallback copies the tree with symlinks preserved verbatim, compares file, directory, symlink and byte counts, and only then removes the original. If any part of that fails, the original is left completely untouched and the failure is logged.

Gotchas and landmines

Each one cost somebody an afternoon, or will

SymptomCause, and why it is that way
You grep the repo and get results from code you are not editing GroundControl.app/ and Vantage.app/ are built bundles sitting untracked in the working tree, each with its own copy of server.js and lib/. They are gitignored, so git status is clean and they are invisible in diffs. Vantage.app is older: its server.js is 57.5 KB against the real 94.7 KB, so it is a stale build under a former name. Delete both, or exclude them from every search.
rg silently skips test/sources.test.js That file contains a literal NUL byte, inside the string on line 37 that proves normalizePath rejects one. Ripgrep classifies the file as binary and reports "binary file matches" instead of your hits. Use --text when searching the test directory.
The README says the scan is cached 5 seconds; it is 30 CACHE_TTL_MS = 30000 at server.js:171, with a comment explaining that a TTL near the 5-second agent poll triggered a synchronous re-walk roughly every 10 seconds. The README was not updated. Trust the code.
A timeout message mentions 10 minutes; the timeout is 20 TIMEOUT_MS = 20 * 60 * 1000 at lib/generate.js:32, but the failure string at lib/generate.js:1004 still says "the 10-minute limit". Cosmetic, and exactly the kind of thing that makes a reader distrust the rest.
Anyone on your network can read any watched project server.listen(port) binds every interface, and the loopback check is applied to three route groups only: /api/comms/*, /api/sources mutations, and /api/complete. /api/doc, /api/raw, /api/open, /api/forge/* and POST /api/reclaim/:id/trash carry no such check, so from the LAN they will serve files, launch an editor, generate an artifact, and move a folder to the Trash. The comment at server.js:2024 reasons about the sources routes specifically; the others appear to have been left open rather than argued for.
A chat agent edits files with no permission prompt By design: --permission-mode bypassPermissions at lib/comms.js:328, because headless mode has no terminal in which to answer a prompt. The compensating guards are the loopback check, one turn at a time (three across the app), a 20-minute ceiling, a killable detached process, and a cwd taken from the scan rather than from the request.
A chat turn survives kill -9 on the server Also by design. Children are detached into their own process group so stopping one reaches whatever its Bash calls left behind, which means only the shutdown hook reaps them. So the pid is written to comms.json immediately, and the next start matches it against the command line and one of that chat's own session UUIDs before signalling (lib/comms.js:790). A narrow match, because a recycled pid is the one way this could hit an unrelated process.
A project you renamed loses its "complete" mark Marks are keyed by absolute path (lib/marks.js:48), which is the right key against id churn and the wrong one against a rename. Both failure modes are real; the code chose the one that fails visibly.
Deleting a folder from the dashboard does nothing on disk Removing a source only edits sources.json. Moving a folder is Reclaim, behind a typed confirmation. Two different verbs that both read as "remove" in the UI.
Two constants in two files must hold a relationship PROC_TTL_MS (6,000, lib/agents.js) must stay above AGENT_POLL_MS (5,000, server.js), and CACHE_TTL_MS (30,000) above it too. Nothing enforces either. Break one and the only symptom is a core burning quietly at idle.

If you are picking this up, start here

In this order, each small enough to finish in a sitting

  1. Run npm test and record what actually passes. This is the untested assumption everything else rests on: the README claims 99 tests in about 5 seconds, and several tests shell out to git and start real servers on ephemeral ports. You need to know the suite is green on your machine before you trust it as a safety net.
  2. Delete Vantage.app/ and GroundControl.app/ from your working tree. They are gitignored build output, half the bytes in the checkout, and a permanent source of misleading grep hits. Rebuild with ./build-app.sh when you need one.
  3. Start the server against a throwaway config: node server.js --config /tmp/gc/sources.json --root ~/somewhere. Both the marks file and the chat index follow --config into that directory, so you can experiment without touching your real dashboard state.
  4. Decide about the open routes. Either bind to 127.0.0.1 in server.listen, or extend isLocalRequest to /api/open, /api/forge/* and the Reclaim trash route. This is a one-line change either way and it closes the gap described in the landmines table.
  5. Fix the two documentation drifts: the 5-second cache claim in README.md and the "10-minute limit" string at lib/generate.js:1004. Cheap, and they are the two places where a careful reader currently learns not to trust the prose.
  6. Widen npm run check, or replace it. It covers six files out of twenty-odd. A glob over lib/*.js would be honest; a real linter would be better and would be the project's first dev dependency, which is a decision to make deliberately.

  • lib/util.js first, 320 lines. It holds the ignore list, the language table and resolveInside, and every other module leans on it.
  • lib/scan.js next. It is the shape of the whole product: one walk, hard budgets, never throws, and the ProjectSummary every other feature decorates.
  • server.js from the top to the route() function at line 516. That is the original server; everything below it was appended feature by feature under banner comments, and each banner states that feature's safety posture.

What to keep, if you change everything else

Three properties hold this codebase together, and each one is enforced in more than one place because the author clearly did not trust a single guard. Keep them, or the tool stops being safe to point at a folder you care about.

  • Every path is checked three ways, syntactically, after path.resolve, and after fs.realpath, against the folder the project was scanned from. Reclaim then runs the same gates a second time, independently, right before it moves anything.
  • Nothing fails a scan. Every walk, every git call, every transcript read is wrapped so a broken project degrades to a partial card rather than blanking the dashboard. A failed scan serves the last good payload.
  • Reading is free, writing is confirmed. Exactly three actions touch anything outside Ground Control's own directories: saving an artifact, moving a folder to the Trash, and a chat agent working in one project. All three are explicit, and the third says so in the UI under the box you type into.
